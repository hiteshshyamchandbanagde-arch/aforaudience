UI/UX Design System — As-Is vs. To-Be

What's locked and consistent today, what's still legacy debt, and what has never been formally specified — plus how to mature each gap, whether Figma Make should be part of that, whether the palette is centrally configurable in code, and where animation/infographics/interaction could differentiate the product. Built to support a go/no-go call on scoping a dedicated design-system pass.

05 Improvement Scope — Decision Inputs

Four gaps, ranked by how often they cause rework today.

No written type scale

Font sizes/weights/line-heights are set from memory per-component. Causes inconsistency risk every time a new screen is built.

HIGH — touches every new screen

No formal spacing/grid system

Layout spacing is implicit per-component on both platforms; no shared unit to check new work against.

HIGH — compounds with the above

Admin mobile content responsiveness

All 8 Admin pages got the mobile nav shell but not mobile content layout — real gap if Admin is ever used on mobile in practice.

MEDIUM — depends on actual Admin usage pattern

Legacy token residue

Not a spec gap — a cleanup backlog. Surfaces reactively whenever an old file is touched (e.g. BUG-2609-024/025).

LOW — handled opportunistically, working as intended

Component library / single source of truth

Buttons, inputs, and modals are styled per-file, not from shared components — this is why the token cleanup keeps recurring (BUG-2609-024 fixed 2 files; more still exist).

HIGH — root cause behind the token-residue backlog above

Icon system

No documented icon set, sizing, or stroke-weight rules. Only caught in passing as a "nit" so far (e.g. Users/Artists search using an eye icon instead of a search icon), never formally audited.

MEDIUM — cosmetic today, compounds as more pages ship

Accessibility spec

No written contrast, focus-state, or reduced-motion rules. The dark theme's limited palette makes silent contrast failures easier to introduce and harder to catch than on a lighter theme.

MEDIUM — currently unverified, not necessarily broken

Motion / animation guidelines

Intro-splash typing animation, card-load spinners, and nav transitions exist ad hoc with no rule for when motion should or shouldn't be used.

LOW — nothing currently broken, just undocumented

Breakpoint definitions

The mobile/desktop split at 1023px is used consistently in code but never written down as a named, reusable breakpoint set.

LOW — works today by convention, risks drift over time

06 How to Mature Each Gap

Suggested approach only — no action taken. Each row can be scoped independently.

GapMaturing approach
Type scalePick 5–6 sizes (e.g. 12/14/16/20/28/34px) with weight + line-height per level; document in docs/afa-design-tokens-reference.md; retrofit opportunistically like legacy-token cleanup.
Grid / spacingAdopt an 8px (or 4px) base unit; define page-margin/gutter rules per breakpoint; same doc as above.
Component libraryExtract Button/Input/Modal from the worst-offending files first (already flagged for legacy tokens); require new UI to use them going forward.
Icon systemAudit current icon usage across nav + dashboards; pick one size scale and stroke weight; consolidate into a single icon component.
AccessibilityRun one contrast/focus-state pass against the 4 locked tokens; document pass/fail combinations so future work doesn't re-derive it each time.
Motion guidelinesCatalogue existing motion (splash, spinners, transitions); write one rule for when motion is used vs. not, rather than per-component judgment calls.
BreakpointsName the existing 1023px split (and any others in use) as tokens/constants in one place, referenced everywhere instead of re-typed per file.

07 Should Figma Make Help? Useful, with a caveat

Yes for exploration, no for trust. It's already been used well to generate options fast for real decisions (nav placement, wordmark variants) — it's genuinely good at producing several directions quickly.

The caveat: this project's own working notes flag that Figma Make "repeatedly produces confident change descriptions that don't match rendered/grepped reality." Every past exploration that was actually shipped required a manual code-vs-Figma diff before being trusted — never taken on its self-report alone.

Net: use it to widen the option set, not to validate what's already built or to skip the verification step.

08 Is It Centrally Configurable? Mostly — adoption is the gap, not the system

The 4 locked tokens live as CSS variables in globals.css. Changing one there cascades everywhere it's referenced by variable — but only where a file used the variable instead of a hardcoded literal.

WORKS Token referenced correctly
background: var(--afa-fill-solid)
// change --afa-fill-solid once in globals.css →
// this button updates automatically, everywhere it's used
BREAKS Hardcoded literal instead
background: var(--afa-terracotta)  // legacy token, off-palette
color: "white"                     // hardcoded literal, not a token at all
// changing globals.css does nothing to this button

Every legacy-token find (BUG-2609-024, BUG-2609-025) is really this same failure: not a broken system, but a file that opted out of it. The system is centralized; adoption isn't yet 100%.

09 Creative Opportunity — Animation, Infographics, Interaction, Transitions

AFA's audience is live art and creative people specifically — this is where the platform can differentiate on feel, not just function. Ideas below are exploratory, not scoped.

CategoryIdeaWhy it fits AFA
Animation Staggered event-card reveal on scroll, echoing a stage curtain / spotlight cue rather than a generic fade. Reinforces "live event" feel instead of a generic SaaS list.
Animation Booking-confirmation moment — a ticket "stamping" or seat "lighting up," not a static success banner. This is the platform's one true celebration moment — currently under-designed.
Infographic Artist journey timeline — visual trail of past shows/venues on the artist profile. More scannable than a text list; reinforces discovery.
Infographic Navarasa mood map — a visual wheel/cluster of emotional event categories. Navarasa is already AFA's core discovery philosophy but is currently text-only.
Interaction Seat-map hover previews — instant sightline/price on hover. Reduces back-and-forth taps during booking.
Interaction Extend the swipe gesture already piloted on the Feedback panel to Discover browsing. Reuses a pattern already built and verified; native mobile feel.
Transition Shared-element transition: event-card image/title morphs into the detail page instead of a hard cut. Visual continuity between browse and detail states.
Transition Role-switch transition (Audience ↔ Organiser ↔ Artist) — a deliberate color/theme shift moment. Reinforces that the user is stepping into a different role on the platform.

Sequencing note

All eight ideas above should wait on the Motion Guidelines gap (Section 06) being defined first. Building any of them ad hoc now adds to the same inconsistency problem already flagged for tokens and components — one rule for "when motion is used" should exist before more motion gets added.

10 Additional Gaps — Specific to a 15–35 Audience Not yet addressed

Function has already been verified as working end-to-end. These are UI/UX-layer gaps that matter specifically because AFA's audience skews young and social-media-native — not general polish items.

AreaGapWhy it matters for 15–35
Personalization No documented approach to a personalized/algorithmic Discover feed; no visual split between "For You" and "Trending Near You." This age group expects adaptive feeds (Instagram/Spotify norms), not a static list.
Social proof / FOMO No visual pattern for "X people viewing," "3 tickets left," or friend-attendance cues. High-impact on booking decisions for this demographic specifically; currently absent entirely.
Shareability Event cards have no design treatment for looking good as a shared screenshot/story. This audience discovers events via peer shares more than in-app browsing.
Empty / loading / error states Writing tone is guided ("errors don't apologize") but there's no visual spec for empty states (no events in city, no bookings yet). Shapes first-time-user impression, which is disproportionately important for retention at this age.
Onboarding Role selection, permission asks (location/notifications), and the intro splash exist but aren't tied together as one designed first-run sequence. First 60 seconds is where this demographic decides to stay or churn.
Dark-mode-only Not a gap — a decision point. App is dark-theme-only currently. Dark-mode-native audience, but outdoor-readability/accessibility tradeoffs are worth naming explicitly rather than assumed.
Notifications web-push exists in the stack but has no visual/content design system — tone, timing, visual identity. Notification design is a major retention lever specifically for this age group.
Search & filters Functionally flagged already (BUG-2609-023, search no-op). Even once fixed, no visual design exists for filter chips, applied-filter state, or empty-result guidance. Functional fix alone won't feel complete without the visual layer.
Micro-copy / tone Writing principles exist (active voice, no apology in errors) but haven't been audited across the app for consistency. Voice consistency reads as more important to this audience than to an enterprise-tool audience.

11 Strategic Call — Before Any More Spec Work

Everything above is infrastructure. Infrastructure doesn't make someone love a product — one moment, done perfectly, does. Three calls, in priority order.

1. Own one moment, not ten

Section 09 lists eight animation/interaction ideas, all weighted equally. That's wrong. Pick the single moment someone would screenshot and send a friend — the strongest candidate is the decision to go, not the payment — and make everything else quieter so that moment is the loudest thing on the screen.

2. Say no to a second accent color

Section 08's suggestion of an "excitement" accent color is worth reconsidering. Restraint, not addition, creates drama. Keep the CTA orange sacred and single-purpose. If a moment needs to feel electric, earn it with motion — motion is free to iterate on; a second brand color is a commitment you'll be undoing in six months.

3. Ship the type scale and grid before Figma Make, not after

Not the exciting work — the necessary one. A one-page spec, boring and finished, beats a beautiful screen that can't be repeated. Everything creative built on top of an undefined scale/grid looks like chaos eventually, no matter how good any single screen looks in isolation.

12 How to Proceed

Sequence, not a simultaneous push. Each step should be finished and boring before the next one starts.

StepActionDone when
1Write the one-page type scale + 8px grid spec (Section 06).It fits on one page and nobody needs to ask "what size is this?" again.
2Decide the one signature moment (Strategic Call #1) — write one sentence describing it, no committee.You can say it in one sentence without hedging.
3Design and build that one moment only — obsessively, ignoring the rest of Section 09/10 for now.You'd show it to someone outside the team and they'd react.
4Extract the component library from the worst legacy-token offenders (Section 06), so the signature moment doesn't get diluted by inconsistent buttons/inputs around it.Zero legacy-token hits remain in the files touching that moment.
5Only now bring in Figma Make — for the remaining Section 09/10 ideas, against the finished spec from steps 1–4.Every Figma Make output is checked against real code before being trusted, per Section 07.
6Revisit accessibility, motion guidelines, icons, notifications, onboarding — in that order, opportunistically, not as a blocking project.Each gets its own one-page spec, same discipline as step 1.

The one-line version

Finish the boring spec, decide the one moment, build only that, then let Figma Make loose on everything else — never the other order.
